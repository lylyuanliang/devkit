## Context

**Current State:**
- `MessageConsumer.tsx` 仅是占位符 ("coming soon")
- `ConsumerGroupsView.tsx` 存在但仅显示列表，无详情功能
- `ConsumerGroupService` 后端有完整的 API（获取组信息、offsets、重置 offset）
- `KafkaConsumerService` 支持消息消费
- 无 Lag 历史数据存储
- 无冷启动指引

**Constraints:**
- 需要与现有的多环境架构兼容
- 需要轻量级实现（不要引入过重的依赖）
- 需要支持暗黑模式
- Lag 监控需要实时更新但不能过于频繁（避免性能问题）

**Stakeholders:**
- Kafka 管理员（需要监控消费进度）
- 应用开发者（需要调试消费行为）
- 新用户（需要友好的入门体验）

## Goals / Non-Goals

**Goals:**
- 提供完整的消费者组详情页面，展示组信息、成员、消费进度
- 支持查看具体的消费消息内容（message key、value、timestamp）
- 实现 Lag 实时监控和历史趋势展示
- 优化冷启动体验，引导新用户创建消费者组或体验演示功能
- 保持用户在单一详情页面内完成 90% 操作（无需频繁跳转）

**Non-Goals:**
- 不实现消费者组的完整 CRUD（仅显示和监控，删除保留但不是重点）
- 不实现基于时间范围的消息过滤（仅查看最近消费的消息）
- 不实现消费者应用性能分析（超出范围）
- 不实现多消费者组对比（后续功能）
- 不实现消息内容的结构化解析（Avro、Protobuf）

## Decisions

### 1. 详情页架构：标签页设计

**决策：** 使用标签页（Tabs）组织详情页，而非分离的多页面

**标签设计：**
```
┌─ MessageConsumer ─────────────────────────────────────┐
│                                                       │
│  [← Back to Groups] Group: my-consumer-group          │
│                                                       │
│  ┌─ Overview ─┬─ Progress ─┬─ Monitoring ─┐         │
│  │            │            │               │          │
│  │ • Group ID │ • Offsets  │ • Lag Chart  │         │
│  │ • State    │ • Messages │ • Metrics    │         │
│  │ • Members  │            │              │         │
│  │            │            │              │         │
│  └────────────┴────────────┴──────────────┘         │
│                                                       │
└───────────────────────────────────────────────────────┘
```

**理由：**
- 用户不需要在多个页面间跳转
- 保持上下文和滚动位置
- 移动端友好
- 符合现代 SPA 设计模式

**实现：**
- 使用 React 状态管理当前标签
- 各标签使用独立组件
- 标签切换时不重新加载数据（保持缓存）

### 2. Lag 数据存储和更新策略

**决策：** 内存缓存 + 定期轮询，而非持久化存储

**方案对比：**
| 方案 | 优点 | 缺点 |
|------|------|------|
| **内存缓存** | 简单、快速、无额外依赖 | 页面关闭后丢失历史 |
| **数据库存储** | 永久历史、更专业 | 引入复杂度、维护成本高 |
| **IndexedDB** | 浏览器本地、持久化 | 兼容性考虑 |

**采用内存缓存** 理由：
- 这是管理工具，用户关心的是当前会话的监控
- 实现简单，不增加部署复杂度
- 足够满足实时监控需求
- 可在 store 中维护最近 N 条 lag 记录

**实现：**
```typescript
interface LagHistoryEntry {
  timestamp: number;
  consumerGroup: string;
  topic: string;
  partition: number;
  lag: number;
}

// 在 store 中维护
const [lagHistory, setLagHistory] = useState<LagHistoryEntry[]>([]);

// 定期轮询（每 5-10 秒）
useEffect(() => {
  const interval = setInterval(fetchLagMetrics, 10000);
  return () => clearInterval(interval);
}, []);
```

### 3. 消息查看的实现深度

**决策：** 查看消费者组消费的实际消息（不是 ad-hoc 消费）

**交互流程：**
```
消费进度表格
  ├─ topic-A, partition 0, offset 1000, lag 50
  │   ▼ 点击行
  └─ 弹出 Modal 显示最近消费的 N 条消息
      ├─ 向后翻页（查看更早的消息）
      └─ 关闭返回表格
```

**为什么是 Modal 而非新页面：**
- 用户查看完后立即返回进度表格，无需重新加载
- 轻量级，不中断当前上下文

### 4. 图表库选择

**决策：** 优先使用 Recharts（如已依赖）或轻量化解决方案

**评估：**
- Recharts: 轻量、React 友好、配置简单 ✅
- Chart.js: 重一点，但文档完整
- 自定义 SVG: 过于复杂，维护成本高

**选择 Recharts** - 如果项目未依赖，使用简单的 SVG 或 Canvas 手绘

### 5. 演示消费者组的实现

**决策：** 创建临时消费者组，由工具在后台自动消费指定 topic

**实现方式：**
```typescript
// 创建演示组
const createDemoConsumerGroup = async (topic: string) => {
  const groupId = `demo-group-${Date.now()}`;

  // 使用 KafkaConsumerService 创建消费者
  const consumer = await kafkaService.createConsumerForTopic(topic, {
    groupId,
    fromBeginning: false, // 从最新开始
  });

  // 启动消费
  await consumer.subscribe(topic, onMessage);

  // 在 UI 中刷新组列表
  return groupId;
};
```

**特点：**
- 自动命名（demo-group-<timestamp>）
- 自动消费，UI 立即显示进度
- 用户可以看到实时的 lag 数据和消费过程

## Risks / Trade-offs

| 风险 | 影响 | 缓解方案 |
|------|------|--------|
| **Lag 轮询频率过高** | 网络/CPU 压力，用户体验差 | 设定合理的轮询间隔（10秒），UI 中显示"最后更新时间" |
| **内存中 lag 历史过大** | 浏览器内存溢出 | 限制历史记录数量（最近 100 条），定期清理过旧数据 |
| **消息查看加载慢** | 用户等待时间长 | 预加载前几条消息，虚拟滚动显示大量消息 |
| **演示消费者持续消费** | 资源浪费，用户迷惑 | 自动停止（5 分钟无交互），在 UI 中提示可手动停止 |
| **新用户不知道如何离开引导界面** | UX 困惑 | 提供"跳过"按钮，或在有真实组时自动隐藏 |

**权衡：**
- **功能完整性 vs 实现复杂度**：优先实现核心功能（详情、消息、Lag），高级功能（历史对比、导出）后续迭代
- **实时性 vs 性能**：轮询间隔 10 秒，足以满足监控需求而不过度消耗资源
- **内存使用 vs 功能丰富**：限制历史数据条数，保持轻量

## Migration Plan

**部署步骤：**

1. **第一阶段：基础架构**（2-3 天）
   - 实现 MessageConsumer 容器组件
   - 创建标签页框架
   - 实现 Overview 标签（组信息、成员）

2. **第二阶段：核心功能**（3-4 天）
   - Progress 标签：消费进度表格 + 消息查看 Modal
   - Message viewer 组件：显示实际消息内容

3. **第三阶段：监控面板**（2-3 天）
   - Monitoring 标签：Lag 图表和实时指标
   - Lag 轮询逻辑和历史数据管理

4. **第四阶段：冷启动和演示**（2-3 天）
   - 实现 Onboarding 界面
   - 实现演示消费者组创建功能
   - 集成使用指南链接

5. **第五阶段：测试和优化**（2-3 天）
   - 性能测试（大量消息、高频 lag 更新）
   - 跨浏览器测试
   - 用户体验测试

**回滚策略：**
- 如果新 MessageConsumer 有问题，可快速回滚到占位符版本
- 各标签独立实现，可逐个禁用有问题的标签
- 演示功能通过特性开关控制
